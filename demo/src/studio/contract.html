How the escrow contract works

UsdcEscrow holds USDC for a job until a verdict signed by the escrow's verifier settles it. The buyer can pay early, the seller can refund early, and after the deadline anyone can return the money to the buyer. Nobody else, including the contract's owner, can move the funds anywhere.

Lifecycle

Each escrow is a small state machine. Every settlement function first requires the status to be Funded and then moves it to a final state, so an escrow settles exactly once and a verdict can't be replayed.

The three final states are terminal. Calling any settlement function on them reverts with NotFunded.

The escrow id ties everything together

The escrow id is a hash of the buyer and every term. Because the same id is the funding signature's nonce and the subject of the verdict, neither signature can be reused for different terms.

The verdict signature

A verdict is EIP-712 typed data, so a browser wallet shows the fields in readable form before you sign. Signing costs nothing; the seller later submits the signature in a transaction.

domain {
  name:              "UsdcEscrow"
  version:           "1"
  chainId:           84532        // Base Sepolia
  verifyingContract: <escrow address>
}

Verdict(
  bytes32 escrowId,   // which escrow
  uint256 toSeller,   // the rest goes to refundTo
  uint64  expiry      // the signature's own lifetime
)

The domain binds the signature to this contract on this chain, so it can't be replayed on another deployment or network. The studio gives each signature a 15-minute expiry.

What executeVerdict checks, in order

  1. The escrow is still Fundedelse NotFunded
  2. The deadline hasn't passedelse DeadlinePassed
  3. toSeller is at most the escrowed amountelse AmountExceedsEscrow
  4. The verdict hasn't expiredelse VerdictExpired
  5. The signature is from the verifier stored with this escrow: a normal key (ECDSA) or a smart-contract wallet (ERC-1271)else InvalidVerdictSignature

The owner's only power is setVerifier, which applies to escrows funded afterwards. Each escrow keeps the verifier it was created with, so rotating the key can't affect money already locked. The contract is not upgradeable and not pausable.

Payout safety

One party can't block the other

Payouts are pushed. If a transfer fails, for example because Circle has blacklisted the payee or paused USDC, the amount is credited to owed[account] instead of reverting. A blacklisted seller therefore can't freeze the buyer's refund share. Anyone can later call withdraw(account), and it pays only that account.

Exact amounts, no re-entry

Funding compares the contract's USDC balance before and after, and reverts with UnexpectedAmountReceived if it got anything but amount, so a future fee-on-transfer USDC can't under-collateralize an escrow. Every function that moves USDC is nonReentrant (OpenZeppelin's transient-storage guard), and status is updated before any payout.

Known limits

  • If Circle blacklists the escrow contract itself, all funds in it are frozen. No contract design can avoid this.
  • Refunds after the deadline need someone to send a transaction and pay gas; nothing happens on its own.
  • No platform fee, no top-ups, and no deadline extensions: changing any term means a new escrow.
